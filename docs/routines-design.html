the flock of ducks

design record · settled 2026-07-04 · duck ≥ v0.18 · supersedes flock (never deployed)

A workspace is an employee, not furniture. Claude in the main pane is the manager; the sidebar is its flock of executors — codex runs, shells, artifacts. Pads are team memory. Channels are how the manager tasks and reads its people. A routine is the workspace's job description. This was implicit in the original main-pane-is-claude design — routines make it official.

The one correction that shaped everything

Schedules drive executors; events drive the manager. Routines launch and continue codex runs on the clock. The manager claude is woken only by their reports — completion events delivered up the channel — never polled by a timer. A scheduled manager beat remains possible (target = "manager"): event-driven is a trusting manager, scheduled check-ins are rigor. Real management mixes both; trust is merely the default.

timer tick ──schedules──▶ codex executors (runs tab, cwd = project) │ work; rollouts record everything ▼ tick notices new task_completes ──batched digest──▶ claude (manager) │ "arm-watch done: '2% move, earnings-driven'" ▼ claude manages: tail detail · redirect executors · write pads update pane title ──▶ visible in ⌂ workspaces to you / motherduck

One channel fabric, three edges

An endpoint is any pane you can send-keys into plus a transcript you can tail. Codex executors have rollouts; claude managers have their own session transcripts (~/.claude/projects/…jsonl) — structural twins. So there are three edges, not three systems: down, up, lateral. Addressing is duck channel send --workspace <ws> <pane>, with manager reserved for the workspace's main claude pane. @duck_parent (a session option) forms the tree — flexible: any workspace may parent others. motherduck is the invariant root: one workspace, always exists, default parent; its roster flips scope so child workspaces render as its agents. Its standing routine #1 is the secretary — a heartbeat executor that diffs the org and reports notable changes as ordinary digests. The org's bookkeeping is expressed entirely in the system's own primitives.

Routine format — duck-native

<project>/.duck/routines/<name>.toml   ← trigger + target + overrides
<project>/.duck/routines/<name>.md     ← the prompt (the job description)
fieldvaluesmeaning
triggercron · heartbeat · manualwhen the tick fires it (schedule / interval alongside)
targetrun (default) · managerrun = codex executor pane; manager = a scheduled turn to claude (the rare check-in)
reportdigest (default) · nonewhether completions are couriered to the manager
trigger × targetwhat happens
run + cron/manuala fresh codex exec pane per fire, cwd = project root, kind runs; exit-hold keeps failures visible
run + heartbeatone persistent codex TUI pane; each beat = duck channel send of the prompt — recurring turns in one thread, watchable in the viewport
managera scheduled turn sent to the main claude pane (claude ensured running first)

Concurrency guard: a routine whose pane is still working is skipped, not queued — missed beats drop; heartbeats are idempotent by design.

The tick (every minute, systemd timer — the evict-sweep pattern)

  • Projects = live workspaces' @duck_dir ∪ ~/.duck/routines-projects (registered by duck routines enable, so automation survives every workspace being closed).
  • Due-ness from last-fire state in ~/.duck/routines-state.json (one small JSON, like names.json).
  • Fire per the table; a missing workspace is created headless so runs are always inspectable.
  • Courier: same pass tracks rollout offsets and delivers one batched digest turn to the manager when new task_completes exist — send-keys, dependency-free; claude --channels upgrades delivery to structured events when present.

Phases

  1. Format parsing + tick + cron/manual runs + runs tab. The meat.
  2. Heartbeats + the report courier + roster affordances (ran-history over rollouts, last message one Enter away).
  3. motherduck + @duck_parent + the secretary + org-scoped roster view.

Non-goals

No HTTP/WS API or MCP remote surface — the hub runs everything; claude-on-hub is the control plane. No app-server thread pooling — pane-per-run until scale forces otherwise. No second run-ledger — rollouts are the history. No daemon — a timer, tmux, and files.
