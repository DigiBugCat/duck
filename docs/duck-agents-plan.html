duck · design note

Agent runners you can watch, click into, and supervise

The whole system is three layers on top of plain tmux. Nothing new runs in the background, nothing is stored twice: tmux windows are the agents, a file codex already writes is the event stream, and one small adapter feeds it all to Claude.

layer 1 · built The sidebar — where agents live on screen

You work in your normal duck session. duck spawn codex puts codex in a hidden twin session next to yours (one tmux window per agent) and opens a right-hand column: the top pane is a live window onto the selected agent, the bottom pane is the clickable roster.

The trick that makes the top pane interactive rather than a screenshot: it is a second tmux client attached to the twin session. Selecting an agent is just tmux switching windows — so the pane you're looking at is the agent, keystrokes and all.

layer 2 · designed One agent, two lanes — you type, machines read

The problem we're solving: we want both. A human wants the full codex TUI to watch and type into. A supervisor (Claude, a script) needs structured input/output. Codex already gives us both from a single process — every session it runs, TUI included, is journaled to a rollout file (JSONL events: user message, agent message, task started, task done).

Nothing is duplicated. The rollout file records everything that happens in the window — what you typed, what the supervisor injected, everything codex did — so both lanes always agree. Pairing a window with its rollout happens once at spawn (match folder + timestamp) and is then pinned to the window.

layer 3 · designed One big channel into Claude — metadata does the routing

Claude Code's channels feature lets an outside system push events into a running Claude session. The catch: channels are fixed when the session launches. So we don't make a channel per agent — we make one channel, duck-agents, and let agents come and go inside it. Every event carries {session, agent} so Claude always knows who's talking, and its single reply tool uses the same metadata to route back.

The sidecar pushes only what's worth interrupting for — turn started and turn finished (with the agent's final message). The full play-by-play stays available on demand via duck channel tail. And because a reply is typed into the agent's real window, you can literally watch Claude talk to codex in your viewport.

why it stays simple The rules that kept the parts count down

tmux is the database.

Which agents exist, what they're called, which rollout is theirs — all stored as tmux window options. Kill the window, the record is gone. Nothing to sync, nothing to clean.

Reuse the stream codex already writes.

No wrapper process, no log tee. The rollout file was already the source of truth for codex's own resume feature; we just read it.

One channel, forever.

Claude channels can't change mid-session, so the launch-time surface is a single name. All the dynamism lives on our side, where it's free.

Injected input is visible input.

Supervisor messages go through the same keyboard the human uses. No hidden side conversations with your agents.
